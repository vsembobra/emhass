# Universal battery management — Phase 0 plan

Repository reviewed at `9f3a1158`. This plan is the Phase 0 deliverable. Phase 1 starts after approval, and each subsequent phase has its own review. Later file names and interfaces introduced below are proposals.

## Goal and integration approach

Accept normalized solar and storage telemetry and recommend an hourly SOC floor that a site adapter can interpret. Prioritize serving critical load during outages, then using on-site solar and avoiding curtailment, then tariff savings. The enabled service defaults to ADVISORY and can publish recommendations. Actuation requires a separate, explicit opt-in. The service and its new features default off in EMHASS. Keep the hard SOC minimum, command limits and stale-data policy in deterministic code outside the models. Keep reinforcement learning and vendor integrations outside this project.

Build and backtest a vendor-neutral reserve and baseline before changing the optimizer. Reuse EMHASS forecast inputs, the existing SOC constraint and publication where they fit. An external-only planner could ship advisory floors through the existing interfaces, with horizons and intermediate targets limited to what the public API already accepts. Integrating immediately inside `Optimization` would expose the full horizon but tie the reserve rules and simulator to optimizer internals. The proposed staged approach gets an independent backtest and needs only a small solver integration for the first deployment. Start the Phase 5 integration with single-battery MPC, subject to approval. Keep site data isolated by site and preserve pack identity for a later multi-battery allocation policy.

## Shared contracts for later phases

- Use timezone-aware UTC instants, explicit interval duration and kW/kWh in the new domain code. Use nonnegative PV and load, positive grid import and battery discharge, and SOC fractions. Convert to W/Wh once at the EMHASS boundary and to percent at the HA/device boundary. Use site-local time only for calendar features and the optional hour-of-day reserve profile. Keep both occurrences of a repeated hour in replay and optimization.
- Use one forecast grid per request. Record forecast issue and validity timestamps, availability of each input and fallback status. Derive optimizer steps and hourly recommendations with explicit interval boundaries. A device floor for an interval governs discharge during that interval. The solver floor is an end-of-step energy constraint, so an outage starting at a step boundary needs its pre-charge target on the preceding step. An outage starting now requires checking measured SOC.
- Treat reserve energy, the hard physical floor, and a forecast SOC trajectory as distinct quantities. While grid power is available, hold reserve above the hard floor. When a measured or modeled outage begins, allow critical load to draw on that reserve down to the hard floor. Report a shortage if energy, islanding support or discharge power is insufficient. Capacity and forecast models are advisory inputs and cannot move the hard limits.
- Add only opt-in config and output fields. For each new EMHASS parameter update associations, packaged defaults and the UI schema, then verify structural versus runtime handling in `OptimizationCache`. Preserve existing forecast and output contracts, logs, zero-config behavior and dry-run isolation. Put implementation docs under `docs/`. Use small phase commits and pytest coverage. Discuss visible output and solver changes with maintainers before proposing an upstream PR. [Configuration and cache workflow](docs/develop.md#adding-a-parameter) · [Repository rules](AGENTS.md)

## Phase 1 — Outage history and reserve

1. Add a pure `src/emhass/reserve.py` and a small local event store. Proposed store is SQLite under the data path with site keys and transactional upserts for replay or concurrent imports. The module takes normalized voltage/status samples or CSV events and uses UTC start/end and `measured` or `scheduled` provenance. Keep an open event explicit and detect/coalesce duplicate or overlapping measured intervals before taking statistics. Keep scheduled windows distinguishable even when they overlap measured ones. Treat missing grid readings as unknown. Keep sensor selection, voltage thresholds, debounce and restore thresholds at the ingestion boundary. **Verify** repeat imports, restart after an open outage, overlap, gaps, schedule cancellation and site isolation with `tests/test_reserve.py`.
2. Implement `reserve_kWh = P_critical_kW × T_outage_h / efficiency`, `usable_capacity_kWh = nominal_kWh × SoH × allowed_depth` and `reserve_SOC = floor_soc + reserve_kWh / usable_capacity_kWh + margin`, with the SOC coordinate to be agreed before device mapping. Use one-way discharge efficiency measured at the relevant delivery boundary. Let `quantile` default to 0.90 and `window_days` to 14. Use the maximum duration with fewer than five completed measured events. Use load during measured outages or the hourly critical-load P90, with an explicit cold-start baseline. Configure `margin`, `decay_days`, `floor_soc` and `profile_mode`. Decay the historical uplift smoothly from the last measured outage to baseline. Reset on a new event and optionally limit the uplift to hours with historical outages. **Verify** `1.5 × 3.8 / 0.92 = 6.19565 kWh`, or about 0.620 of a 10 kWh usable band before margin. Cover no events, one event, the five-event switch, decay/reset, empty hours and invalid capacity or efficiency.
3. Emit the general reserve and scheduled pre-charge requirements separately. Merge overlapping scheduled windows for energy accounting. Size the deadline against available lead time and release the pre-charge requirement as energy becomes usable for outage service. If reserve energy exceeds capacity or the requested floor exceeds the permitted maximum, recommend the maximum and report the shortfall, with a separate flag for an unreachable deadline. **Verify** a scheduled outage changes its pre-charge window only, and capacity, power and lead-time shortfalls remain visible. Document the rule and limits in `docs/battery_reserve.md`.

## Phase 2 — Baseline and simulator

1. Add the policy as a pure function in a proposed `src/emhass/battery_planning.py`. Find the first hour where PV P10 is at least load P90, then integrate the positive shortfall `max(load_P90 − PV_P10, 0)` up to that hour, convert it to stored energy using discharge efficiency, add outage reserve and clamp the result to the permitted SOC range. Use explicit quantile inputs in this phase. A deployment that only has existing point forecasts can use a documented deterministic fallback marked as such. Proposed behavior for no crossover is to integrate through the available horizon and mark the requirement incomplete beyond it. Define how the calculation treats a scheduled outage already represented in the load shortfall so the same energy is counted once. **Verify** immediate and absent crossover, variable interval length, saturation, signed input validation, and outage spend-down.
2. Add an offline replay module, proposed `src/emhass/battery_backtest.py`, and `tests/test_battery_backtest.py`. Compare fixed SOC and the rule with the same starting SOC, equipment constraints, weather/telemetry availability, tariff and outage realizations. Add a planner callback for Phase 5. Simulate grid availability, PV curtailment, battery charge and discharge limits and efficiencies, critical-load priority, and actual unmet energy. Policy sees data available at decision time. Replay sees subsequent actuals after the decision. Report imported kWh, curtailed kWh, duration with unmet critical load, and net tariff cost when available. Also report unserved critical kWh and on-site solar use so equal outage hours or exported energy do not obscure a worse outcome. **Verify** hand-calculated energy and cost fixtures, zero grid exchange during outage, unavailable history, mixed tariffs and repeatable chronological replay. Document replay inputs, metrics and the fixed-SOC comparison in `docs/battery_backtest.md`.
3. Use the same held-out replay for every later candidate. Proposed acceptance is no deterioration in outage service, then a measurable solar improvement, then cost as the tie-break when the first two are equivalent. Define thresholds, outage exposure and the fixed floor before comparing results. Report trade-offs or inadequate data explicitly. **Verify** a cheaper candidate with more unmet critical load fails the acceptance rule.

## Phase 3 — Load quantiles

1. Add an opt-in CPU LightGBM quantile forecaster in a proposed `src/emhass/load_quantiles.py`, with an optional dependency and tests. Fit P10/P50/P90 with hour, weekday, holiday flag, temperature, lag values 24 elapsed hours and 7 elapsed days back, and a trailing station mean fitted from available history only. Include day-of-year sine/cosine features once the training fold has at least 12 months of history. Define holiday calendar and missing-lag handling before fitting. For leads beyond a lag's observed range, use a causal prediction or a documented missing-feature strategy shared by training and inference. **Verify** feature parity, no future leakage, the 12-month boundary, ordered finite predictions and no LightGBM import for default installs.
2. Attach the bundle alongside existing load forecasting before Phase 5 chooses its optimizer input. Use `Forecast.get_load_forecast` and its normal optimizer-facing validation for the existing and fallback paths. Reuse the chronological comparison ideas in `forecast_calibration.py` and benchmark against the actual `MLForecaster` workflow and naive on identical issue times and horizons. Report P50 MAE, each quantile's pinball loss and observed P10–P90 coverage by lead. Use `tests/test_load_quantiles.py` and document the opt-in path in `docs/forecasts.md`. **Verify** a walk-forward split, cold-start fallback and quantile ordering after physical clipping.

## Phase 4 — PV quantiles and weather archive

1. Add an opt-in PV quantile model in a proposed `src/emhass/pv_quantiles.py`. Reuse pvlib and the PV geometry/modeling in `Forecast`; build a clear-sky power denominator on the same AC/DC measurement basis as observed PV, using coordinates, tilt, azimuth and kWp. Fit CPU LightGBM P10/P50/P90 to measured output divided by clear-sky power for meaningful daylight values. Reconstruct physically bounded PV power and emit zero at night. Use forecast irradiance, cloud layers, snow depth, hour and day-of-year. Exclude training intervals where SOC is near full and export is disabled or limited. Track that censoring with telemetry evidence and report excluded/unknown coverage, since the heuristic can also remove genuine low generation. **Verify** finite predictions near sunrise, physical bounds, censoring, and missing/invalid model fallback to the configured PV method without applying point bias/correction twice.
2. Add a provider interface and a site-scoped append-only archive in a proposed `src/emhass/weather_archive.py`. Capture each successfully fetched distinct forecast with model, issue/receipt and UTC validity times and retain daily snapshots. Keep the existing latest-forecast cache for its operational purpose. Align each training row with the forecast available before its decision time. For backfill use provider forecasts. Open-Meteo Historical Forecast stitches early lead times from successive runs, so use it only where it demonstrably matches the issue/lead contract. Use Single Runs or lead-specific Previous Runs for evaluations that need a full day-ahead vintage and leave unsupported history uncovered. Record provenance and document CC BY 4.0 attribution and the separate noncommercial terms of the free endpoint before commercial deployment. **Verify** as-of selection, archive deduplication, retention of older vintages, and exclusion of reanalysis or a run published after the simulated decision. Add `tests/test_pv_quantiles.py`, `tests/test_weather_archive.py` and provider notes under `docs/`. [Historical Forecast API](https://open-meteo.com/en/docs/historical-forecast-api) · [Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api) · [Open-Meteo terms](https://open-meteo.com/en/terms)

## Phase 5 — MPC integration and advisory publication

1. In `command_line.py`, select configured quantiles after forecast preparation and before the MPC solve (proposed enabled defaults are PV P10 and load P90). Pass one deterministic pair on the existing grid. Keep PV aggregation and any per-plant series consistent. Keep Phase 3/4 fallbacks visible in the plan. When enabled, the policy determines the minimum reserve independently of tariffs. Evaluate the existing self-consumption/cost behavior in the backtest. If dispatch must enforce solar use ahead of cost, scope a separate opt-in priority objective after defining how to value on-site use versus curtailment and export. **Verify** selected inputs at the solver boundary and compare the full pipeline against the fixed floor at the priority order agreed in Phase 2.
2. The smallest proposed solver patch is an optional normalized floor vector from `perform_naive_mpc_optim` through `perform_optimization` to the existing `param_soc_target_floor`. Validate finite SOC fractions, exact horizon shape, equipment bounds and battery membership before solving. Compose the floor and legacy point target using the elementwise maximum in numeric code after converting each battery's fractions to Wh. Reuse the existing constraint with no additional variables. Reset every call, including absent profiles, within `_solve_lock` and preserve the zero-vector behavior when disabled. Values are runtime data; horizon and battery topology still determine shape in the cache. Keep absolute physical bounds and legacy recovery semantics. Make conflicts with recovery, terminal targets, discharge power, availability and charging lead time explicit. If the added floor is unreachable, publish an advisory shortfall/fallback status and suppress actuation. Use existing grid caps for scheduled isolation only where the balance remains feasible. Modeling load shedding in the dispatch solver would require a separate balance change with an explicit unmet-load variable. The simulator already records unmet load. **Verify** step boundaries, composition with legacy targets, shape/validation errors, infeasible and repeated cached calls, no leakage across concurrent runs, and equality with legacy outputs when disabled. Add focused coverage to the MPC/optimization and cache suites.
3. Publish an additive hourly floor via `publish_data` and `RetrieveHass.post_data`, with a distinct recommendation sensor and full timestamped profile, generation/expiry, reserve shortfall and fallback status. Keep `SOC_opt` as the solved trajectory. Propose maximum-of-steps when exporting a conservative hourly floor, with explicit expiry and UTC boundaries. For an adapter with N slots, merge adjacent intervals conservatively, using each merged interval's maximum as a candidate. Validate calendar/timezone support, bounds, reachability and outage release after compression. If there is no safe representation, expose the advisory profile and the reason. **Verify** N=1, enough slots, DST repeated hours, a pre-charge deadline that would move under compression, legacy CSV/publish contracts, dry runs and stale or infeasible result handling. Add a dedicated publisher test and document the floor and status fields.

## Phase 6 — Retraining and monitoring

1. Add an opt-in externally scheduled nightly job using the existing command-line dispatch pattern or a small separate entry point that does not create an optimizer. Validate timestamp gaps, units, outliers and energy balance nightly, then train on a rolling window when the weekly or monthly cadence is due. Compare candidate and active model on the same last N weeks using archived as-of features. Promote only on improvement under agreed error, coverage and outage replay criteria. Write immutable versioned artifacts and JSON metadata (training and holdout ranges, data source, feature/schema version, metrics and model version). Atomically advance a per-site active pointer and retain the previous version for one-step rollback. Existing point-model files retain their format and audience. **Verify** a worse challenger, interrupted writing, concurrent nightly starts and rollback while predictions are running.
2. Track daily MAE, signed bias and observed P10–P90 coverage by lead using forecasts as issued. On sustained drift, flag/alert and switch to the Phase 2 rule with its deterministic fallback inputs. Keep alert delivery outside the model. Monthly, use `BatteryIdentification` and its validated charge/discharge segments as the first reuse candidate. If the fit yields `capacity_wh` across one unit of reported SOC, convert to `kWh per 1% SOC = capacity_wh / 100000`. Require the agreed full-cycle or sufficiently deep-cycle evidence, report confidence and staleness, and keep the result advisory. **Verify** drift and recovery across missing actuals, malformed metadata, sparse cycles and the capacity conversion. Add `tests/test_battery_retraining.py` and a runbook under `docs/`.

## Phase 7 — Adapter contract and safety guard

1. Formalize `TelemetryFrame`, `DeviceCapabilities`, `Command` and the abstract `Adapter` in a proposed `src/emhass/battery_adapter.py`. The early domain data shapes can carry UTC interval timestamps, kW power channels, SOC, grid status, site/pack identity and quality. Capabilities include `soc_floor_slots`, SOC bounds, device write rate and supported modes. A command carries the validated profile, target identity and expiry. Provide `DryRunAdapter` to capture commands in memory for tests and an HA sensor publisher that delegates to the Phase 5 publish path for recommendations. Keep the HA wrapper at the integration boundary. **Verify** capability validation, time/unit conversions, advisory publication and zero device calls for either implementation.
2. Add a deterministic `SafetyGuard` ahead of any future actuation adapter. Enforce explicit actuation opt-in, hard min/max, the maximum floor change per step, the minimum interval between writes and an upper write rate. Check freshness, plan status and reachability when sending. Use a site-configured safe advisory default on stale data. Allow a future device fallback command only under explicit authorization and known device limits. Write authorization and rate checks must remain atomic per device across retries and concurrent requests, with state carried across restarts if a future adapter can write. Fail closed when constraints conflict or device state is unknown. **Verify** `tests/test_battery_adapter.py` against stale sensors, low SOC, rate/step limits, retries, conflicting caps, overlapping requests, and advisory mode with the flag off. Document contracts and the HA automation boundary in `docs/`.

## Decisions for approval and main risks

1. **SOC coordinate and reserve math.** The specified 62% is a fraction of the usable band. EMHASS and devices report a fraction of their full reported SOC span. Approve whether `reserve_kWh / usable_capacity_kWh` is a normalized usable-band increment to map back before publishing, or is intentionally added directly to a device SOC fraction as a conservative policy. Define the margin's coordinate, the source of SoH and allowed depth, and whether the reported 10 kWh is already derated. For example, a 10 kWh usable band with 80% depth represents 12.5 kWh across the full span, so 6.20 kWh adds about 0.496 to device SOC under the band mapping. Subtracting a hard floor twice or treating round-trip efficiency as discharge efficiency will misstate the reserve.
2. **Critical-load and outage semantics.** Identify the critical-load meter or configured fallback, grid status/voltage source, transition thresholds, treatment of unreliable intervals and precedence of CSV versus measured corrections. Set no-history reserve, decay shape, local-hour profile selection, scheduled pre-charge lead time, and behavior when an hour with `PV=load=0` qualifies as crossover. Confirm which circuits have islanding capability and which batteries can serve them. Reserve planning cannot cover an outage beyond deliverable energy or instantaneous power.
3. **Acceptance and tariffs.** Choose the fixed SOC floor, replay sites and dates, outage sample sufficiency, acceptable differences in unserved load, solar and net cost, and tariff assets (import, export, any demand charges). Confirm if a lower-curtailment plan that exports more while using less solar locally satisfies priority two. If priority two must be enforced in optimizer dispatch, that goes beyond a forecast and SOC-floor input patch.
4. **Weather and models.** Pin forecast issue schedules and lead times for backfill, determine the commercial provider tier and archive retention, and choose thresholds for PV censoring, holdout size, drift and seasonal coverage. Sparse outages, biased censoring and a fixed-lead archive used for the wrong horizon can make apparent gains unreliable.
5. **Deployment and control.** Confirm first-site topology, single-battery MPC as the initial integration, hourly slot boundaries, floor resolution, minimum interval, maximum step change and safe stale default. Confirm separate permissions for advisory publishing and device actuation, and how existing HA automations subscribe to the new recommendation sensors. An hourly or compressed schedule can make an urgent floor change unachievable. The guard needs a defined behavior for that case before any device writes are considered.
